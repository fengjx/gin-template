# 00 Brief

## 问题重述

- `internal/service/option.go` 当前把缓存 map、并发控制、全量加载和定时刷新都揉在一起，难以复用。
- 仓库缺少一个放在 `pkg` 下、可以承接类似“全量快照缓存”场景的最小通用组件。

## 用户与场景

- 后端服务开发者需要在 `internal/service` 或 `internal/biz` 中复用轻量缓存能力。
- `option` 服务需要继续保留当前对外接口，但把通用缓存职责下沉。

## 价值判断

- 降低 `option` 服务复杂度，让业务代码只关心值读取、错误映射和写库后刷新。
- 为后续类似配置表、字典表、元数据快照缓存提供统一基础能力。

## 已知事实 / 推断 / 假设

- 当前仓库还没有通用缓存抽象，`option` 是唯一一个同时做懒加载和后台刷新循环的服务。
- 本次只需要支持“全量 loader -> 内存快照”模型，不需要单 key loader 或 TTL。
- `option` 外部函数签名和数据库结构必须保持不变。

## 主要风险

- 前缀语义若处理不一致，可能导致 `GetAll` 或 loader 结果暴露错误 key。
- 自动刷新若重复启动或停止不干净，可能造成重复加载或 goroutine 泄漏。

## 最小落地路径

- 在 `pkg/cache` 提供最小接口：`New`、`Run`、`Get`、`GetAll`、`Set`、`Refresh`、`Del`。
- `option` 层二次封装 `GetAndCache` 语义和业务日志。
- 补齐 `pkg/cache` 与 `option` 的单测，完成 feature 文档闭环。
