# Code Review 基线

这份文档定义仓库统一的 review 行为。`flow-review`、PR review 和人工复查都以此为准。

## 输出方式

- findings-first，先列问题，再给摘要
- 按严重度排序
- 每条 finding 都要说明：现象、风险、建议、影响范围
- 没有问题时也要写残余风险与未覆盖项

## 严重度

- `P0`：阻塞合并，存在明显错误、安全风险、数据破坏、不可恢复回归
- `P1`：高优先级，功能行为错误、核心链路缺测、上线风险高
- `P2`：中优先级，边界条件、可维护性、局部回归风险
- `P3`：低优先级，文档、风格、非阻塞优化建议

## 必查项

### 规格一致性

- 是否与 `docs/features/<NNN>-<slug>/20-tech-spec.md` 一致
- 是否出现未记录的规格漂移
- bugfix 是否先经过 `70-bug-log.md` 调查闭环

### 行为正确性

- 是否满足原始需求与验收标准
- 是否引入回归
- 空状态、失败路径、权限路径是否被覆盖

### 测试与验证

- 是否补了与改动直接相关的测试
- 是否运行了正确的命令矩阵
- 测试报告是否写进 `50-test-report.md`

### 工程约束

- 是否遵循 OpenAPI / 配置 / 数据库 / 前端约束
- 是否修改了生成文件或绕过既定入口
- 是否引入与仓库现有风格冲突的新约定

### 上线风险

- 是否需要额外发布说明、配置变更、迁移步骤
- 是否影响 GitHub / CI / 运行环境
- 是否存在未关闭但可接受的残余风险

## 无 Finding 时的写法

至少给出：

- 已检查的范围
- 未覆盖项
- 残余风险
- 最终结论：`通过`
